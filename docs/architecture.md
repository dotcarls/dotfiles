# Machine, dependency, and identity architecture

## Invariants

1. Machine role and trust domain are explicit local data, never inferred from a
   hostname, path alone, or whether a command happens to be installed.
2. Public source contains no work endpoint, organization, vault/item, username,
   email, or credential-routing value in plaintext. Work-only metadata is
   ASCII-armored `rage` ciphertext; actual secret values remain in 1Password.
3. Personal GitHub material is authorized only on macOS and stored in Keychain
   or in passphrase-protected OpenSSH keys whose passphrases Keychain protects.
4. Remote and container profiles start with no personal or work secret access.
5. The rendered Brewfile is the complete machine-global union. Bundle cleanup
   is never automated and is never invoked with `--force` by managed helpers.
6. Project code cannot obtain ambient secrets merely because `.envrc` was
   approved. Secret access requires a separate, explicit process invocation.
7. Homebrew paths are generated by `brew shellenv`; architecture-specific
   prefixes are not duplicated through shell fragments.
8. The 1Password SSH agent is selected only by the encrypted work SSH config;
   it is never exported as the ambient shell agent. Personal HTTPS Git auth and
   Apple-agent commit signing therefore remain isolated from work identities.
9. The dedicated Homebrew GitHub API token is loaded from Keychain only inside
   a `brew` child process. It is not ambient shell state or package-registry
   authentication.

## Profile matrix

| Role | Homebrew default | GUI/MAS default | Development default | Work config default | Secrets default |
|---|---:|---:|---:|---:|---:|
| macOS laptop/desktop | on | on | on | work domain only | work domain only |
| persistent Linux remote | on | off | on | off | off |
| bare-metal/VM workstation | on | explicit | on | explicit | off |
| container | off | off | off | off | off |

All defaults can be overridden during `chezmoi init`; granting work config or
secrets is an intentional local decision. `managed` and `manageGuiApps` are
separate so MDM ownership can coexist with a Homebrew-managed CLI toolchain.

## Source-state boundaries

- Small content differences use templates.
- Whole-file capability differences use `.chezmoiignore`.
- Machine facts and identity values live only in mode-`0600` chezmoi config.
- Work routing and helper implementations use the `encrypted_` source-state
  attribute with `encryption = "age"` and `age.command = "rage"`.
- A read-source-state pre-hook retrieves the native X25519 identity from a
  secret reference stored only in local chezmoi config. The cached identity is
  `0600`; its parent is `0700`.
- Scripts are idempotent or content-triggered. Package installation is not run
  implicitly by `chezmoi apply`; operators keep a reviewable dependency
  boundary through `dotfiles-brew`.

Ignored work targets are absent on a newly initialized unauthorized machine.
Changing an already-authorized machine to a less privileged profile does not
silently delete old files; deprovisioning must be reviewed separately because
ignore is not secure erasure.

## Rage key policy

Use native age X25519 identities generated by `rage-keygen`. SSH recipients are
not used: `rage` cannot use `ssh-agent`, hardware-backed SSH identities are not
supported by that path, and SSH recipient tags make ciphertext linkable.

The work identity is a domain recovery identity. Do not provision it to normal
remote hosts. If a persistent host genuinely needs encrypted work state:

1. Generate a host-native identity on that host.
2. Add only the host recipient and the work recovery recipient to that host's
   narrowly scoped ciphertext.
3. Keep the host identity local; keep the recovery identity in 1Password.
4. Do not bake either identity or an `OP_SERVICE_ACCOUNT_TOKEN` into an image.

Multiple recipients are independent full-access grants, not shards. A future
personal recipient must not be added to work ciphertext.

### Rotation

1. Create the replacement identity and retain the old identity temporarily.
2. Re-encrypt only the affected trust domain to old and new recipients.
3. Verify from a clean authorized endpoint using only the new identity.
4. Re-encrypt that domain again without the old recipient.
5. Retire local old identities and update 1Password.
6. If compromise caused rotation, rotate underlying credentials too: Git
   history encrypted to the old recipient remains decryptable by the old key.

Never run a blanket mixed-domain `chezmoi re-add --re-encrypt`; an active global
recipient configuration can accidentally widen access.

## Homebrew reconciliation

The manifest deliberately includes every supported machine-global mechanism
that Bundle can represent: taps, formulae, casks, MAS apps, VS Code extensions,
Go tools, uv tools, and npm tools. Two historical duplicates are retired by
intent: `rage` replaces `age`, and the Homebrew `claude-code` cask replaces the
duplicate global npm installation. Existing copies are only reported by the
cleanup preview until an operator chooses a separate removal action.

Applications lacking a Homebrew receipt are not emitted by `brew bundle dump`,
and MAS discovery can be incomplete when Spotlight is unhealthy. The managed
inventory helper therefore also enumerates application bundles and App Store
receipt paths. Brew-adoptable applications are declared as casks or MAS entries;
vendor-only, archival, legacy, and MDM-owned applications are recorded as
explicit comments in the rendered common or encrypted work Brewfile. Adopting
an existing application may require a reviewed reinstall; the helper never
forces or overwrites an app automatically.

Safe lifecycle:

1. `dotfiles-brew inventory` and review Bundle, app, and receipt state against
   profile intent. Use `inventory-bundle` when a valid Brewfile snapshot alone
   is required.
2. Edit package data or the encrypted work extension.
3. Render and inspect `~/.Brewfile` with `chezmoi diff`.
4. `dotfiles-brew check`.
5. `dotfiles-brew apply` to install missing entries without a general upgrade
   pass (Homebrew may still upgrade a dependency required by an installation).
6. Use `dotfiles-brew upgrade` only when upgrades are the explicit objective.
7. Use `dotfiles-brew cleanup-preview`; investigate every proposed removal.

Third-party work formulae carry item-level `trusted: true` only where this
repository intentionally accepts the tap. New third-party taps require review;
trust is never granted globally.

`conjur-cli` is a deliberate third-party exception. The repository is exposed
as the explicitly addressed `dotcarls/pinned` tap, and its formula pins each
supported OS/architecture release asset to an immutable URL and SHA-256. It
does not patch CyberArk's tap and does not execute a GitHub release lookup while
Homebrew loads package metadata. Release discovery and checksum review happen
at maintenance time, before the formula change is committed.

Homebrew documents `HOMEBREW_GITHUB_API_TOKEN` for GitHub REST requests and
`HOMEBREW_GITHUB_PACKAGES_TOKEN` for the GitHub Packages registry. The managed
wrapper reads the former from the dedicated macOS Keychain item only for each
`brew` child process. A `brew.env` file is intentionally unsuitable because
Homebrew does not execute commands or expand shell expressions in those files,
and storing the token there would put it in plaintext.

This process boundary limits ambient exposure; it is not a sandbox. Homebrew
tap definitions are executable Ruby with the user's privileges, and
`HOMEBREW_GITHUB_API_TOKEN` is available to Homebrew while it runs. The token
is therefore required to have no scopes beyond GitHub's inherent
public-repository access and a bounded lifetime, and it is never reused for Git
authentication or package publishing. Only explicitly reviewed formulae
receive item-level trust.

## direnv boundary

Managed `direnv.toml` disables stdin, implicit `.env` loading, and non-strict
evaluation. It defines no whitelist. Local allow/deny records and cache data are
never synchronized.

The managed `direnvrc` blocks the common accidental transitive loaders on
direnv 2.37.x. This is defense in depth, not a sandbox; approved `.envrc` code
can still execute arbitrary same-user commands. Therefore:

- `.envrc` may select toolchains, paths, and public feature flags.
- `.envrc` may not invoke 1Password, Keychain, or rage.
- Work secrets enter only a named child process through a reviewed 1Password
  Shell Plugin or `op run -- command`.
- Personal GitHub tokens remain inside the GitHub CLI/Keychain credential
  protocol and are never exported as `GH_TOKEN` or `GITHUB_TOKEN`.
- Headless workloads receive narrowly scoped runtime credentials from their
  execution environment, not from chezmoi or direnv.

When direnv adds authorization for transitive files in a stable release, this
policy can be revisited; it must not assume unreleased `require_allowed`
behavior.
